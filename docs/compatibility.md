# Agent compatibility

当前兼容性工作的重点是“共享记忆的入口与出口 Adapter”，不是简单判断客户端是否能连接 MCP。Capture 负责读取本机 Agent 公开扩展面暴露的可观测对话，Injection 负责把已批准记忆带回下一轮 Prompt，MCP 负责按需深度查询和交接。Trae、Claude Code 与 Codex CLI 已验证同一通用 Adapter 契约的三种不同实现。

The connector matrix records the supported integration contract. A detected CLI is not automatically modified; users run `open-continuity connect <agent>` explicitly. Existing MCP entries are never replaced unless `--force` is supplied, and the connector backs up the client configuration first.

## Storage Core compatibility

### Stage 5 bounded read runtime

`MemoryService` now applies `bounded-reads-v1` to Recall/Context/History/Handoff and Query's nested storage reads. Default ordinary read timeout is 1500ms, at most 16 admitted read requests and 8 outstanding Store reads per instance. These are validated immutable constructor policies, not new tool arguments or tenant quotas. Query keeps its Profile/request timeout and structured timeout/abstain result. Normal response bodies/ranking/cursors remain; ordinary timeout adds `READ_TIMEOUT`/504, admission rejection `RUNTIME_BUSY`/503, closing `RUNTIME_CLOSED`/503. Storage failures remain errors, not empty hits. Custom clients must handle these additional error codes.

Timed-out driver reads retain capacity until actual settlement. No automatic retry, hidden queue or driver hard cancellation is advertised. Synchronous SQLite can block the event loop beyond the deadline; results are checked after completion. Direct Store/Retrieval usage is outside this service-level guard. SQLite `busyTimeoutMs` optionally changes post-initialization lock waiting (default unchanged); migration/initialization has its original retry budget. Default PostgreSQL factory Pool limits acquisition to 2000ms, statements to 5000ms and locks to 2000ms with max=10; custom pools must configure their own bounds. These are server limits, not precise request cancellation.

`close()` marks closing and rejects while actual operations drain; `closeGracefully(5000)` waits within a bounded monotonic budget and closes at most once, never force-releases active sessions. HTTP/MCP process shutdown handles failures explicitly. Optional in-process observers get only frozen operation/outcome/timing/count/stage metadata; default off, no text, identity, path or credentials. Observer exceptions do not change results; callers must keep callbacks nonblocking.

Capability discovery adds actual `readRuntime` policy and reflects the actual frozen Query policy. No memory/package schema, SQL migration, ranking or Adapter protocol change. Shared store/permission tests, real-process SIGKILL recovery and PostgreSQL evidence do not establish power-loss durability, multi-tenant source authentication, snapshot reads or production SLO. See [design](./retrieval-core/phase-5-runtime-reliability.md).

### Stage 4B/4C budgeted evidence and answer

Query's `sufficiency` now measures the budgeted Context (`sufficiencyVersion=budgeted-context-v1`), not all retrieved evidence. `retrievalSufficiency` preserves the old assessment for explicit audit comparison. Empty Context yields insufficient; missing subqueries/minimum evidence, unfinished execution, history not projected or bounded candidate truncation yield partial/insufficient. History event/version metadata remains available in `evidence`, but cannot imply a complete historical answer. Users relying on retrieved counts must migrate to `retrievalSufficiency`; this is an intentional public semantic change, not a silent reinterpretation of old values.

`ContextPackResult.coverage` adds `context-coverage-v1` with actual selected query-match coverage and omission reasons. Query defaults to greedy `query_coverage` packing, maximizing new query coverage then breaking ties by 4A rank; constructor `queryPacking=rank_only` is an explicit ablation. It is a consumption policy, not a semantic reranker or a globally optimal compression algorithm. Ordinary memory_context ordering, whole JSON rendering and token/count defaults are unchanged; identical snapshots deduplicate, independent ids do not semantically merge, and mixed snapshots fail with STORAGE_ERROR.

Query adds `answer` (`evidence-answer-v1`, `memory_projection`) with original structured values, exact-version citations, per-query coverage and evidence_ready/partial/abstain. No model-generated summary, objective truth, semantic answerability or source authentication is claimed. Statements/citations only refer to actual Context items; cite ids are content fingerprints, not permission grants or signed sources. Answer metadata is separate from the Context token budget, which is an estimated rendered-context budget, not a cap on total JSON transport size. No new HTTP route/MCP tool, storage schema, package format or Recall cursor change. Existing identity/private/confirmation/workspace and fail-open boundaries remain.

Capabilities report budgeted sufficiency, query packing, coverage version and explicit nonsemantic projection/citation support. See [stage4](./retrieval-core/phase-4-context-and-answer.md), [4B](./retrieval-core/phase-4b-budget-and-coverage.md) and [4C](./retrieval-core/phase-4c-evidence-answer.md). The lower stage4A sections retain its first incremental scope; 4B/4C are now implemented only within this deterministic contract, not free-form RAG answering.

### Stage 4A Context selection

Default `memory_context` and Query Context Pack ordering now uses `context-selection-v2`: exactTier, retrieval score, exact-tie-only purpose preference, then updatedAt/id. Scope and confirmation remain gates/annotations, not additive boosts. Default ordinary Context still permits unconfirmed memories; confirmation-required consumers retain their stricter policy. Private, user/agent/task and workspace boundaries are not broadened. A batch with missing retrieval scores preserves input order and explicitly reports fallback; legacy upstream positional scores are not advertised as native relevance.

Core `ContextPackPolicy.selectionMode` accepts `relevance_first` (default), `relevance_only` (ablation) or `legacy_weighted` (old ordering). This is a constructor policy, not a new MCP/HTTP request argument. Consumers relying on old ordering must explicitly opt into legacy weighting; it retains the known weight overrides and lack of Exact-tier precedence. Policy objects are validated and detached at construction, so later mutation cannot silently change filtering.

Responses add optional `selection` fields at the pack and item levels. `priority` remains numeric but its default scale is now the unrounded retrieval positional score; the complete order is lexicographic and cannot be reconstructed from priority alone. Existing `reasons` remain evidence/eligibility annotations, not proof of boost. Rendered JSON lines and budget defaults/limits, Recall order, cursor fingerprints, memory/package schemas and Adapter code are unchanged. Capability discovery reports actual service selection/confirmation policy and context budgets. See [4A design](./retrieval-core/phase-4a-context-selection.md).

This subsection describes 4A's selection-only incremental scope, not a model reranker. The subsequently implemented budget-aware coverage and projection answer contract are documented in 4B/4C above. Older sections below describe their historical stage scope, including the previously unchanged Context weights.

### Explicit facts (3C)

Optional `fact` declarations are exposed by Remember over Core/HTTP/MCP and retained in current state and events. `group` is caller-defined and exact; actual identity partitions by user, scope, task/ownerAgent and kind. Validity is `[validFrom, validUntil)`; cross-key replacement points to an exact memoryId/sourceEventId/version. Adding, editing or removing a fact requires userConfirmed and expectedVersion. This is approval/audit of a claim, not authentication of its source or proof of truth; CAS protects the written record, not the referenced record.

Legacy/custom stores without `readFactGroup` reject new fact declarations before writing; MCP/HTTP discovery reports `factDeclarations=false`, `factPolicy=null`, `factGroupLimit=0`. Implementing that method commits the Store to the complete declaration persistence contract; Core checks returned event/current declarations and reports STORAGE_ERROR if they were dropped. A lying/failed custom provider may already have written data, so do not assume Core can roll back an external Store—reconcile using the idempotency key and repair the provider. Capabilities describe the implementation, not a successful connectivity/schema readiness probe; migration-disabled databases still require the documented manual migration.

Text Recall applies relevance ranking first, then `explicit-facts-v1`: visible group lookup verifies claims without adding non-query matches. Different surviving JSON values conflict; expired/future/replaced claims, missing or changed references, cycles, truncation or unsupported custom stores are omitted. `retrieval.factReview` explains omissions, and accepted receipts contain `factAssessment`. Group reads preserve identity, includePrivate, confirmation, scope and kind partitions. Query/key restrict returned candidates, not companion proof: limiting verification to a key could hide another visible conflict. Companion records are never added as answers, and hidden data cannot influence the visible result. No-query list/History remain audit/inspection, not fact adjudication.

SQLite automatically migrates to schema 4 and PostgreSQL to schema 3; fact columns and a group index are additive, old rows remain unannotated. Disabling migration does not create the new schema. Back up before upgrade. Runtimes containing the stage-1 schema-version guard reject versions newer than they support; earlier releases do not have this protection and may open an upgraded database while ignoring fact fields. Never run those older releases against an upgraded database. To roll back, restore a pre-upgrade backup into a separate database and use its matching runtime; no in-place schema downgrade is provided. No tokenizer or FTS weights change.

Memory Package 1.1 is required when any event has a fact, including history later forgotten; ordinary packages continue as 1.0. The new importer accepts both and preserves reference IDs when remapping the local user. JSON is compatibility only: fact-bearing ledgers use `schemaVersion=2` / `eventsV2`, intentionally omitting `events` so old readers cannot silently erase fact claims on rewrite. Do not downgrade these ledgers or export packages for old runtimes without an explicit, separately designed conversion.

Query cursor encoding remains v2, but the fingerprint now binds fact policy and group budget; previously issued text-query cursors require restarting. Pagination and fact checks are live/current, not concurrent/time snapshots. Candidate top-K and group budgets are bounded: abstention may leave a page empty, and a replacement that does not match the query is not promoted. Context purpose weights remain unchanged. Model/semantic truth resolution, automatic relation discovery and global/multi-tenant fact verification remain challenges.

Stage 3 now routes built-in public text Recall/Context/Query through `CandidateRetrieval` / `CandidateSearchStore.searchCandidates`, introduced separately in stage 2. The optional MemoryStore method and custom retriever constructor preserve the legacy path; those custom paths do not advertise scored ranking receipts. See [current ranking contract](./retrieval-core/phase-3-ranking.md).

The public response adds rankingVersion, scoreModel, fusedScore, exactTier, evidence and selectionReasons. Existing score/channels/ranks remain available: score is positional, not raw BM25 or a probability. Single-channel fusedScore is null; multi-query evidence uses query_sum with query/step-tagged raw signals. Runtime capabilities identify BM25 vs match-order fallback, exact precedence and zero structured contribution. HTTP/MCP discovery uses the actual service channels and budgets. Legacy custom stores report rankingVersion=null, fullTextRanking=unverified, structuredContribution=null and exactPrecedence=null rather than claiming the scored pipeline. Short SQLite queries remain unscored fallback.

Ranked query cursor v2 binds ranking version, filters/identity, enabled channels, candidateLimit, rrfK, fusion, exact precedence and internal confirmation policy; changing these or presenting an old ranked query cursor returns VALIDATION_ERROR and requires page-one restart. Page size can change. Candidate top-K bounds the entire paginated set and truncated indicates more matches beyond that bound. Plain storage/History cursor v2 and SQL schemas are unchanged; current-state ranking is live, not a concurrent snapshot.

Phase 2C changes only the evaluation-report contract to `open-continuity-candidates-v2`: comparison requires observed judgments, coverage, budgets and matching dataset/evaluator/runtime fingerprints. Legacy v1 reports must be regenerated, not silently accepted. This is not a runtime memory schema, cursor or MCP/HTTP migration. See [2C verification and evidence limits](./retrieval-core/phase-2c-validation.md).

Candidate batches return channel, channelRank, rankMeaning, raw score model/direction and match reasons. Only SQLite long-term FTS hits have native BM25 scores (lower is better); short literal fallback, exact/structured lookup, PostgreSQL substring and JSON/InMemory compatibility use null scores. SQLite multiple literal terms are ANDed, whereas other stores retain full-query substring fallback; equal relevance is not promised across engines. Independent candidate top-K still rejects cursors; public ranking owns its new cursor. No SQL schema migration is required.

Eligibility and optional confirmation are applied before truncation. Identity is supplied by trusted callers, not authenticated by this Core API; workspace and Hook fail-open remain unchanged. SQLite BM25 uses global FTS statistics and is not a per-user statistical-isolation guarantee. Native PG candidate contract tests are distinct from pg-mem retrieval-quality evidence and Team release readiness.

Phase-0 evaluation is separate from runtime compatibility. `eval:baseline` uses a fixed dataset and evaluator against a chosen source checkout; its reports distinguish Recall, Context, safety, stability, capacity and unexecuted engineering checks. PostgreSQL evidence is labeled pg-mem only. No new public protocol or Adapter compatibility is implied by a baseline pass; see [the measurement contract](./retrieval-core/baseline-framework.md).

Concrete stores implement `MemoryRepository.list` for structured listing. The legacy `MemoryStore.recall` facade and custom stores remain compatible; no scored search or relevance ranking is introduced in stage 1. Confirmation remains consumer policy, and eligibility never expands.

Recall/History cursor v2 binds user, agent, task/private and all filters. A page size change is permitted; a filter change or an unbound legacy cursor returns `VALIDATION_ERROR` and requires restarting from page one. Current-state pagination is live keyset pagination, not a snapshot under concurrent updates. No database schema version is bumped; future schema versions fail closed.

PostgreSQL capability changes from `postgres_text` to `postgres_substring`: standard `strpos(lower(...), lower(query))` fallback treats percent/underscore as literal text. Public SQLite text queries now consume BM25 candidates; direct legacy Store recall remains chronological filtering. JSON is compatibility only, with validated ledgers and atomic rename; it does not promise crash durability or stale-lock recovery.

The shared suite reports PostgreSQL-pg-mem separately: reserved JSON keys are explicitly skipped due to emulator loss, and locks/rollback are protocol checks only. Real PostgreSQL has opt-in tests against loopback `open_continuity_test*` databases and disposable schemas; no configured default database is used. See [stage 1 evidence](./retrieval-core/phase-1-storage.md).

The opt-in `test:storage:postgres:docker` command provisions and removes only its own local tmpfs fixture. Native PostgreSQL 17.11 passed the storage conformance/recovery suite in three fresh instances; this does not turn pg-mem quality metrics into native evidence or imply Team release readiness. PostgreSQL pool wrappers must honor/forward `release(true)` to discard uncertain sessions after rollback failure. SQLite now rejects reuse of a Forget event as a Remember receipt, including null values. See the separate [write/recovery](./retrieval-core/phase-1b-writes.md) and [pagination/eligibility](./retrieval-core/phase-1c-pagination.md) contracts.

## Adapter development status

The Trae, Claude Code, and Codex Adapter milestone is feature-frozen for the current beta and now operates in maintenance mode. The shared contract, per-Agent permission boundary, incremental Capture checkpoints, bounded Injection, managed Hook lifecycle, compensating setup transaction, fictional process black boxes, soak tests, quality gates, and installed-package smoke are complete for the stated compatibility matrix.

Adapter development should reopen only when at least one of these evidence-based triggers exists:

- a supported real client version breaks a documented Capture, Injection, MCP, setup, doctor, upgrade, or uninstall path;
- a security, workspace-isolation, data-corruption, checkpoint, or configuration-restoration defect is reproduced;
- a new Agent with a public extension surface is intentionally added;
- measured reliability data shows that a backlog item is causing user-visible failures.

The credential-backed Claude Stop/non-empty Injection smoke remains a verification task, not a reason to redesign the Adapter. Per-thread batch failure isolation, cross-process Receipt serialization, cancellable Injection lookup, and deeper executable provenance checks remain non-blocking backlog items until real failure evidence raises their priority. New feature work should primarily move to Core while these Adapters receive compatibility fixes and real-client regression coverage.

Other products can use the documented MCP stdio command or HTTP API. A client must support custom MCP servers or another extension mechanism. OpenContinuity cannot inject itself into a closed product that exposes neither capability.

MCP server instructions advise capable clients to retrieve relevant context at task start, store only durable information, and create a Handoff Capsule on explicit handoff. The client model and its tool policy still decide whether a tool is called, so tool availability is not a guarantee of automatic invocation.

Trae Conversation Capture reads only content exposed by the local Trae app-server, skips ephemeral side threads and non-allowlisted workspaces during list-based sync, and stages the visible thread in a local Inbox. The current real read probe verified that a visible local thread can be read with user messages, assistant messages, tool calls, compaction markers, and complete-turn status; it reports structure only and does not persist the user's real thread during verification. List-based sync supports app-server pagination, a configurable page size and maximum thread bound, and reports truncation instead of silently claiming a complete scan. The capture watch command performs interruptible foreground polling and reads threads whose update time differs from the durable per-thread checkpoint. Each successful Inbox import advances thread/turn/item watermarks in the same SQLite transaction; failed imports do not advance them. On macOS, `setup trae` manages the per-user launchd service, reloads it after config or installed runtime changes, and exposes layered health through `doctor trae`. Where launchd is unavailable, setup reports that `capture watch` needs a local process manager instead of pretending a background service exists. The generated plist carries only a small environment allowlist and explicitly includes the detected Trae executable directory, because launchd does not inherit the interactive shell PATH. Sync uses a single-instance lock, stale-lock recovery, bounded retry backoff, and persisted success/failure health state. It does not expose hidden reasoning and does not automatically promote candidates into long-term memory.

Trae Injection is also opt-in and local-only. `setup trae --workspace <path>` enables only that workspace, backs up and updates the discovered `hooks.json`, and connects MCP without enabling a global permission bypass. The hook injects only approved public memory, has a bounded local lookup, records no Prompt body, and fails open on timeout or storage errors. Trae does not expose a reliable non-interactive Hook trust state, so `doctor trae` keeps `/hooks` trust and MCP approval as explicit manual checks. The vertical test verifies that the light pack can be followed by an explicit MCP `memory_query` multi-step search against the same shared database; MCP tool invocation remains a decision made by Trae and its model/tool policy, not by the hook.

Claude Code uses only its documented user-level Hook surface. `setup claude --workspace <path>` preserves existing `settings.json` content, writes a backup before mutation, and installs exec-form handlers for `UserPromptSubmit` and `Stop`. The Stop Adapter parses the JSONL transcript, filters OpenContinuity's own injected context and meta/sidechain records, applies the workspace allowlist to individual records, and uses `last_assistant_message` to cover asynchronous transcript lag. Capture is event-driven and therefore needs no watcher service. Active Claude sessions must be restarted after setup so the user-level Hooks are reloaded. OpenContinuity does not disable normal MCP approval.

Codex CLI uses its local `codex app-server --stdio` JSON-RPC surface for Capture. The Adapter initializes the server, lists threads, reads a selected thread and hydrates turns through `thread/turns/list` (with a legacy `thread/read` fallback), then normalizes user/assistant/tool/compaction items into the shared Inbox contract. Reasoning items are retained only as type markers and their content is never persisted. `setup codex --workspace <path>` installs backed-up, idempotent handlers in `$CODEX_HOME/hooks.json` (normally `~/.codex/hooks.json`): `Stop` triggers Capture and `UserPromptSubmit` returns a bounded approved-memory context. Active Codex sessions must be restarted after setup, and the user must open Codex `/hooks` and trust both handlers. The local app-server probe verifies protocol shape and metadata only; it is not a substitute for a real completed Codex turn invoking both hooks.

All three Capture implementations write the same normalized thread/turn/item contract. The provider-neutral read contract passes the previous durable checkpoint to every Adapter; an Adapter may return a full snapshot or a cursor-backed delta, but a delta must return the exact base cursor together with its next cursor. The orchestration layer rejects mismatched source/thread identities and cursor lineage before Inbox import. Claude transcript Capture stores an opaque byte cursor with file identity and a bounded prefix fingerprint, resumes from the end of the last stable JSONL read (including transcripts shorter than the fingerprint window), and falls back to a full scan when the file is rotated, truncated, observably rewritten, or unstable. Codex and Trae currently return full app-server snapshots and still benefit from the same transactional checkpoint contract. App-server pagination rejects repeated cursors and is bounded so a malformed source cannot loop forever.

Raw turns are filtered before import and cleaned by turn age after import, with a default 7-day window. Candidate evidence is separate, defaults to a 30-day pending lifetime, and must be approved before entering long-term shared memory. Exact candidates from different Agents merge their occurrence evidence; deterministic high similarity creates a review warning, and replacement requires an explicit target so the existing memory evolves to a new auditable version. This is conservative duplicate/conflict protection, not model-based semantic reconciliation.

All Injection Adapters use one shared untrusted-memory envelope. Memory text is escaped before it enters the envelope so it cannot synthesize an envelope-closing tag. The configured token budget covers both the selected memory lines and that envelope; the runtime also limits the number of memories, requires approved public visibility, and returns a fail-open empty Hook output when the final rendered payload cannot fit or the lookup exceeds its timeout. Receipts retain only a prompt fingerprint, selected IDs, reasons, timing, and outcome. Granular Injection management accepts `--agent trae|claude|codex` and resolves the implementation through the shared Adapter registry.

Capture and Injection enablement and workspace allowlists are stored per Adapter. Configuration v1 is migrated to v2 with a backup; legacy permissions are assigned only to explicitly connected Agents (or Trae when the old configuration has no owner), never broadcast to all three. Hook installation records an ownership manifest, reconciles stale OpenContinuity runtime paths, and removes only owned/marked handlers during uninstall. All three setup commands execute a reported plan/apply/verify transaction and run reverse-order compensation when a later MCP, Hook, configuration, service, or doctor step fails.

The Codex Adapter remains experimental: it depends on the locally installed app-server protocol and Codex Hook trust state. A real persisted `codex exec` smoke verified UserPromptSubmit injection and Stop Capture through app-server with fictional data, and a real interactive `/hooks → Trust all → prompt` smoke verified the normal trusted-session path. The automated injection assertion used Codex's one-shot `--dangerously-bypass-hook-trust`; new Codex processes may still require their own `/hooks` review depending on the client's trust lifecycle. If a Codex build does not expose `app-server`, the connector falls back to MCP-only compatibility and refuses Capture setup.
